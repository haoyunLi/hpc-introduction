Prepare files on login nodes; run jobs on compute nodes

Before we connect, it helps to know what we’re connecting to. HPC means high-performance computing. A cluster is a group of connected computers, and each computer is called a node. In this diagram, our laptop connects to the head node, which we’ll call the login node.

That’s where we organize files, edit scripts, and submit work. Other people share this node, so we use compute nodes for the heavier analysis. Both kinds of node can access the project files through shared storage. Connecting with VS Code gives us access to those files, but it doesn’t reserve a compute node. Before any of this works, we need an approved account and permission to use the group’s resources.

2.5 · SLIDE 09 · Files in VS Code

Choose home, project, or scratch storage

Before we upload anything, we need to choose where it will live. Home, project, and scratch storage have different jobs.

Home, under /u, is for settings and small personal files. It has a very limited quota, which means a limit on how much space you can use: 100 GiB as the documented soft limit and 103 GiB as the hard limit. If you stay above the soft limit for seven days, new writes stop until you reduce your usage. You can’t expand the home quota, so it’s a poor place to collect large datasets.

Project storage is shared by the group, and the available space depends on its allocation. It has no snapshots—saved filesystem states that let you recover earlier files—so important data need a separate backup plan.

Scratch is temporary workspace. Files are typically deleted after 30 days without access, sometimes sooner if space is tight. Once purged, they can’t be recovered, so move valuable outputs elsewhere.

For our project, we’ll use the full path supplied by the group, where we have permission to save files. The path on the slide is a placeholder. We’ll open that parent folder first, then upload demo into it.

Read the program, options, and path in a command

A command can look like a long string at first, but we can read this one in three parts. head is the program we’re asking to run. The option -n, followed by 5, says we want the first five lines. This is where Slurm comes in. We prepare the script on the login node, then use sbatch to send it to the scheduler. Read a Slurm batch script line by line

This little file is the complete request for our first job. hello.sbatch is just plain text: it tells Slurm what resources we need, then tells the computer what to run.

4.3 · SLIDE 23 · Slurm jobs

Set nodes, tasks, CPUs, memory, and time for a job

I find this easier to understand by counting the boxes. The big box is one node, so one computer. Inside it are two tasks, which represent two program processes across the whole job. Each task has two CPUs reserved. Two tasks times two CPUs per task gives us four CPUs in total. ntasks already counts tasks across all the nodes, so we don’t multiply by the node count again.

A task here isn’t a sample or a file. These boxes show what we’re requesting, rather than every CPU the computer physically has. Depending on the system, a Slurm CPU can mean a core or a hardware thread.

There’s another step between requesting resources and using them. Plain python analysis.py starts one process. Running multiple processes needs a suitable program and launcher, and a multithreaded program needs its own worker or thread setting.

For our actual hello job, we’ll keep it small: one node, one task, and one CPU. --mem=1G requests one GiB of RAM per node. That’s working memory, not disk storage. --time=00:05:00 allows five minutes of running time, with queue waiting excluded. For a real analysis, we’d choose these values based on the software and data.

With those settings clear, we’re ready to submit hello.sbatch.

4.6 · SLIDE 26 · Slurm jobs

Output files and email notifications

These lines let us choose where the job’s messages go. They’re already in the supplied analysis.sbatch template, before the commands that load software and run the analysis.

--output names the file for ordinary program output. --error names the file for error and diagnostic messages. Some programs also put normal progress messages there, so we need to read what the .err file says before calling it a failure.

The useful part of these filenames is %j. Slurm fills that in with the job ID. For job 123457, analysis-%j.out becomes analysis-123457.out. We leave %j in the script; Slurm does the replacement. With these filenames, the logs go into the folder we submit from. If we add a subfolder to the path, that folder needs to exist before submission.

For email, --mail-type selects the events: END for the job ending and FAIL for failure. --mail-user is the recipient, so we put our own address there or remove both mail lines. Delivery depends on the cluster’s email setup. Even with a completion email, we still check the result.

4.7 · SLIDE 27 · Slurm jobs

When the analysis needs a GPU

Some analysis tools can use a GPU, which is an additional processor for software that supports GPU computing. If a tool needs one, we first need an account and GPU partition that our group can use.

In --gres=gpu:GPU_TYPE:1, gpu names the resource, GPU_TYPE is the type name configured on the cluster, and the final 1 requests one GPU per allocated node. We get the valid names from the group’s documentation or support contact.

Reserving a GPU won’t make a CPU-only program use it. Inside an allocated NVIDIA GPU job, nvidia-smi shows the GPU visible to that job and some basic usage information. The GPU also has its own memory, separate from the CPU RAM we request with --mem.

The software needs a compatible environment too, so its installation instructions matter here. Our tiny demo stays on CPUs. Another optional setting is asking for a particular compute node; we’ll look at that next, because a node name and a GPU type refer to different things.

4.8 · SLIDE 28 · Slurm jobs

When a particular node is required

There are two similar-looking options here, but they mean different things. --nodes=1 says, “I need one computer.” --nodelist=NODE_NAME says, “I need this particular computer.” If we use it, NODE_NAME has to be a real compute node in a partition our account can access. We wouldn't put a login node here.

To look at the available resources, we can use sinfo. The -p option picks a partition, and -N lists the information by node. A node appearing in that list doesn't automatically mean our account has access to it.

For most jobs, I'd let Slurm choose a suitable node. Asking for one specific machine gives the scheduler fewer choices, so we may wait longer. It can make sense if the group needs that machine for a hardware test or comparison. But if we just need more memory or a certain GPU type, we can usually ask for that resource directly.

That's how we choose resources. Next, we'll use them to open a compute shell and prepare our software.

The environment stays; activation is per shell

This is a distinction that's easy to mix up: installing a package and activating an environment are two separate steps.

In the top row, pip puts pandas and the packages it depends on into .venv. Those are files in our project storage. They're still there after the compute shell closes.

In the bottom row, activation tells the current shell to use .venv/bin/python. We're selecting files that already exist. We're not reinstalling them, and we're not requesting a compute node. When a batch job starts later, it'll load the same compatible Python module and activate this same environment. Activating it here doesn't activate it in every other terminal or job.

6.6 · SLIDE 40 · Run and check

Common errors and the first useful check

Errors are part of getting a job set up. The useful thing is to look at the message before submitting the same file again, because an unchanged submission will usually hit the same problem.

If a file can't be found, I'd check pwd, then the path and the spelling, including capital letters. If a command can't be found, check its spelling and whether the right module or environment is selected. For a missing Python or R package, check the environment the job actually uses, and install the package there.

OUT_OF_MEMORY means the job exceeded its memory allowance. TIMEOUT means it reached its time limit. Look at --mem or --time alongside the error log and the software's documented requirements before changing the request.

For an invalid account or partition, check that they're an approved pair. For a quota error, quota shows usage and limits. For Permission denied, ask your group to confirm that you can write to that folder.

And when you ask for help, include the job ID, the batch script, the exact error, and the software version. Those details give your lab contact or ICC support something useful to work with. They don't need your password or a copy of the whole dataset.
