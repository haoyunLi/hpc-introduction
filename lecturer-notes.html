1.1 · SLIDE 02 · Access

Prepare files on login nodes; run jobs on compute nodes

Let’s start with what we’re actually connecting to. HPC stands for high-performance computing. A cluster is a group of connected computers, and one computer in that group is called a node. This is the official NCSA overview. Our laptop connects to the head node in the picture—the login node we’ll use in this talk.

Think of that login node as our starting point. We can organize files, edit scripts, and submit work there. It’s shared with other users, so we send the heavier analysis to compute nodes. We do that by submitting a job: a request that says what to run and how much computing power it needs. The scheduler waits until the requested resources are available, then starts the work.

The login and compute nodes can reach the same project files through shared storage. That’s why we can prepare a script in one place and run it on another node. Connecting with VS Code gives us access to those files; getting compute resources is a separate step. First, though, we need an approved account and permission to use our group’s resources.

2.5 · SLIDE 09 · Files in VS Code

Choose home, project, or scratch storage

Before putting files on the cluster, we need to choose a place for them. Home, project, and scratch storage serve different purposes.

Home is under /u, followed by our NetID. It’s for settings and small personal files. Its quota—the amount of space we’re allowed to use—is very limited: 100 GiB as the documented soft limit and 103 GiB as the hard limit. Staying above the soft limit for seven days stops new writes until we bring our usage down. This quota can’t be expanded, so home is a poor place to keep large datasets.

Project storage is shared by the group. Its capacity depends on the group’s allocation, and it’s where we can keep group data, software, and outputs. It has no snapshots, meaning saved filesystem states that could restore earlier files. Important data therefore need a separate backup plan.

Scratch is temporary working space. Files are typically deleted after 30 days without access, and sometimes sooner when space is tight. Purged files can’t be recovered, so any outputs we want to keep need to be moved elsewhere.

For this walkthrough, we’ll use the writable project location our group gives us. /projects/YOUR_GROUP is only a placeholder for that full path, just as YOUR_NETID stands for our own NetID. We’ll open the project location first, then put our demo folder inside it.

3.2 · SLIDE 13 · Shell essentials

Read the program, options, and path in a command

Suppose we want a quick look at the start of our input table. We can use head -n 5 data/samples.csv. It’s easier to read if we take it in three parts.

head is the program. The option -n, followed by the value 5, asks for the first five lines. Then data/samples.csv is the file to read. If the file has fewer than five lines, head just shows the lines that are there.

Everything after head is an argument. Some arguments change what a command does; others give it a value or a file path. Option letters belong to individual commands, so -n can mean something different in another program.

Spaces usually separate arguments. Quotes keep a path together when it contains spaces. The quoted version shown here also works, although data/samples.csv doesn’t need quotes because it has no spaces.

There’s one more piece we need for this example: data/samples.csv is a path relative to our current folder. So before reading or running anything, we need to know where the terminal is working.

4.1 · SLIDE 24 · Slurm jobs

Slurm runs work on allocated resources

We’re ready to run something, but first we need the cluster to give our job some resources. That’s Slurm’s job. Slurm is the scheduling software in the middle of this diagram.

We prepare a script on the login node and send it to Slurm with sbatch. Slurm checks the request. If the resources aren’t available yet, the job waits in a queue. When they are available, Slurm allocates them, which means it reserves them for our job, and the program runs on a compute node.

Both nodes can access the same approved project folder. Our inputs, scripts, and outputs stay there, so we don’t need to copy the whole project to another computer for every run.

Our terminal stays on the login node after we submit. The batch job runs separately and can keep going even if we disconnect the laptop. Later, we’ll also request an interactive compute shell with srun, which is useful for setting up software.

For now, let’s open hello.sbatch and see what a batch request actually contains.

4.2 · SLIDE 25 · Slurm jobs

Read a Slurm batch script line by line

Here’s the whole file for our first job. hello.sbatch is plain text. The top part tells Slurm what we need, and the command at the bottom tells the computer what to do.

The first line selects Bash to read the commands. The lines beginning with #SBATCH are settings for Slurm. We put those before the commands that run the program.

The job name helps us recognize the submission. The account identifies our group’s compute allocation, and the partition selects a queue we can use. YOUR_ACCOUNT and YOUR_PARTITION are placeholders, so we replace them with a valid pair from our group.

The next lines request one node, one task, and one CPU for that task. Then we ask for one GiB of memory per node and a five-minute running-time limit. The clock for that limit starts when the job runs; time waiting in the queue doesn’t count. Finally, echo prints the message into the job’s output.

We’ll edit and save this file in VS Code, then submit it with sbatch. Running bash hello.sbatch directly would treat the #SBATCH lines as comments and run the command on our current machine without requesting resources.

Before we submit, let’s make those node, task, and CPU settings a bit more concrete.

4.3 · SLIDE 26 · Slurm jobs

Set nodes, tasks, CPUs, memory, and time for a job

I find these settings easier to understand by counting the boxes. The big box is one node, so one computer. In this illustration, we request two tasks across the whole job. Each task represents a program process, and each one has two CPUs reserved. Two tasks times two CPUs per task gives us four CPUs in total.

The ntasks value already counts tasks across the whole job. We don’t multiply it by the number of nodes again. And a task here doesn’t mean a sample or an input file.

These boxes show the resources we’re requesting. They don’t show every CPU physically inside the computer. Depending on the system, a Slurm CPU can mean a core or a hardware thread.

Requesting resources also doesn’t automatically make a program use them. For example, python analysis.py starts one process. Running several processes needs suitable software and a launcher, and a program that uses several threads needs its own worker or thread setting.

Our actual hello job is smaller than this illustration: one node, one task, and one CPU. The --mem=1G asks for one GiB of working memory per node, separate from disk storage. The --time value is in hours, minutes, and seconds, so 00:05:00 means five minutes of running time. Queue waiting isn’t included. For a real analysis, we’d choose these values to match the software and data.

For hello, we can keep these small settings. Now we’re ready to submit it.

4.5 · SLIDE 28 · Slurm jobs

Checking the queue and stopping a job

To see our jobs, we use squeue -u YOUR_NETID, replacing YOUR_NETID with our own username. The -u selects the user. Each time we run the command, we get a new snapshot, so we run it again to check for a change.

PD means pending. The job is waiting, and the listed reason helps explain why. R means it’s running on the resources Slurm allocated. Our tiny hello job may finish before we even check.

Once it leaves the queue, we look at the output. For the example job ID, that’s cat slurm-123456.out. We use our own job ID in the filename, and we expect to see My first HPC job. Leaving the queue by itself doesn’t prove that a job succeeded. Missing or unexpected output is something we need to investigate.

If we do want to stop a submitted job, scancel followed by its job ID does that. We’ll let hello finish here. Ctrl+C in a separate log viewer only interrupts that viewer; it doesn’t cancel the batch job.

We’ve now submitted a job and checked its result. For the analysis job, we can make the log filenames clearer and ask for an email when the job ends.

4.6 · SLIDE 29 · Slurm jobs

Output files and email notifications

These lines control where the analysis job’s messages go. They’re already in the supplied analysis.sbatch template, before the commands that load software and run the analysis.

--output names the file for ordinary program output. --error names the file for errors and other diagnostic messages. Some programs also put normal progress messages there, so an .err file doesn’t automatically mean the job failed. We need to read what it says.

The useful part of these names is %j. We leave that in the script, and Slurm replaces it with the job ID. So, for job 123457, analysis-%j.out becomes analysis-123457.out. That gives each submission its own named log.

With these filenames, the logs go into the folder we submit from. If we add a subfolder to the path, we need to create that folder before submitting.

Email is optional. --mail-type chooses the events: END when the job ends, and FAIL for failure. --mail-user gives the recipient. We put our own address there, or remove both mail lines if we don’t want email. Delivery depends on the cluster’s email setup, and we still check the results even if we receive a completion email.

Some analysis tools can use a GPU. It’s an additional processor, and the software has to support it. If our tool needs one, we first need an account and GPU partition that our group can access.

When a particular node is required

A GPU type tells Slurm what hardware we need. A node name goes one step further and asks for a particular machine.

These two options are easy to mix up. --nodes=1 means “give me one computer.” --nodelist=NODE_NAME means “give me this particular computer.” NODE_NAME has to be a real compute node that our account and partition allow. A login node doesn't belong here.

sinfo lets us inspect the cluster's resources. The -p option selects a partition, and -N shows the information by node. Seeing a node in that list doesn't guarantee that our account can use it.

For most jobs, I'd let Slurm choose. Naming one machine gives the scheduler fewer choices, so we may wait longer. It can be useful when a group needs a particular machine for a test or comparison. If we just need more memory or a certain GPU type, we can usually request that resource directly.

The useful way to think about this is that installation changes files, while activation changes what one shell uses.

Common errors and the first useful check

When a job fails, I'd start with the message before submitting the same file again. It often points to a specific part of the setup.

For No such file or directory, pwd tells us where we're working. Then we'd check the path, spelling, and capital letters. For Command not found, we'd check spelling and whether the right module or environment is selected. A missing Python or R package means checking which environment the job actually uses and installing the package there.

OUT_OF_MEMORY means the job exceeded its memory allowance. TIMEOUT means it reached its time limit. We'd look at the log and the software's requirements, then review --mem or --time accordingly.

An invalid account or partition means checking that --account and --partition are an approved pair. For a quota error, quota shows usage and limits. Permission denied is a reason to check that our group has given us write access to the folder.

If we need help, the job ID, batch script, exact error, and software version give someone a concrete starting point. We don't need to send a password or the whole dataset. The official guide and ICC support are good places to turn when we need more help.
