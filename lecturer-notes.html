Prepare files on login nodes; run jobs on compute nodes

HPC stands for high-performance computing. A cluster is a collection of connected computers, and a node is one of those computers. In this diagram, the connection from the laptop reaches a head node, also called a login node.

The login node is where we connect, organize files, edit scripts, and submit jobs. It is shared with other people, so substantial analysis should run on compute nodes. A job is a request to run a program with specified computing resources. The scheduler assigns those resources and starts the program when they become available.

The shared filesystem holds the project files, so both the login and compute nodes can reach them. Opening VS Code does not reserve a compute node. We first need an approved account and the details of the resources we are allowed to use.

2.6 · SLIDE 10 · Files in VS Code

Choose home, project, or scratch storage

These three locations have different purposes. Home, under /u, is for settings and small personal files. A quota is the amount of storage you may use. The documented home quota is 100 GiB soft and 103 GiB hard. The soft limit allows a grace period; staying above it for seven days stops new writes until usage is reduced. Home quota cannot be expanded.

Project storage is shared within the group, and its capacity depends on the group’s allocation. It has no snapshots, meaning saved filesystem states for recovering earlier files. Important data therefore need a separate backup plan.

Scratch is temporary working space. Files are typically deleted after 30 days without access, and space pressure can cause earlier deletion. Purged data cannot be recovered, so move valuable outputs elsewhere.

4.1 · SLIDE 22 · Slurm jobs

Slurm runs work on allocated resources

We prepare and submit a batch job from the login node. Slurm is the scheduling software that handles the request. It may hold the job in a queue until the requested CPUs, memory, and other resources are available. Allocating resources means reserving them for the job. The program then runs on a compute node.

The two nodes can access the same approved project folder. The job reads the inputs and writes its output there, so we do not need to copy the whole project to a different computer for each submission. Slurm is software, not an extra storage location between the two nodes.

After sbatch submits a batch script, our terminal remains on the login node. The job can continue after the laptop disconnects. An interactive job instead gives us a shell on allocated compute resources, which we will use later for software setup. First, we will read the small hello.sbatch file to see what a batch request contains.

4.2 · SLIDE 23 · Slurm jobs

Read a Slurm batch script line by line

hello.sbatch is a plain text file containing resource requests and commands. Its first line selects Bash, the shell that will read the commands. Lines beginning with #SBATCH are instructions for Slurm, and they must come before the commands that run the program.

The job name helps us recognize the submission. The account and partition must be a valid pair for our group: the account identifies the compute allocation, and the partition selects a queue we can use. The remaining requests specify nodes, tasks, CPUs per task, memory, and a maximum running time. The final echo command prints one message.

We edit and save this file in VS Code, then submit it with sbatch. Running bash hello.sbatch directly would run the command on the current machine and treat the #SBATCH lines as comments; it would not request compute resources. The five-minute limit applies after the job starts, not while it waits in the queue. Before submitting, let us clarify how nodes, tasks, and CPUs fit together.

SchedMD · sbatch
4.3 · SLIDE 24 · Slurm jobs

Set nodes, tasks, CPUs, memory, and time for a job

The diagram is a resource-counting example. One node means one computer. The two task boxes represent two program processes across the whole job. Each task has two CPUs reserved, so the request is two tasks times two CPUs per task: four CPUs in total. ntasks already counts tasks across all nodes; we do not multiply by the node count again.

A task is not a sample or a file. These boxes represent resources requested for the program, not every CPU physically installed in the node. A Slurm CPU may be a core or a hardware thread, depending on the system.

Requesting resources does not automatically make a program use them. A plain python analysis.py command starts one process. Multiple processes need a suitable launcher and program, and a multithreaded program needs its own worker or thread setting.

Our actual hello script keeps the smaller settings shown below: one node, one task, and one CPU. --mem=1G asks for one GiB of RAM per node, not disk space. --time=00:05:00 limits running time to five minutes and excludes queue waiting. Real analyses need requests based on their software and data. We can now submit the saved hello file.

4.6 · SLIDE 27 · Slurm jobs

Output files and email notifications

These directives are already included in the supplied analysis.sbatch template. They belong before the commands that load software and run the analysis. --output names the file for ordinary program output, and --error names the file for error and diagnostic messages. A program may send normal progress information to the error stream, so a nonempty .err file does not by itself mean failure.

Slurm replaces %j with the job ID automatically. For job 123457, analysis-%j.out becomes analysis-123457.out. We leave %j in the script rather than replacing it ourselves. With these plain filenames, logs appear in the submission folder. A log subfolder would need to exist before submission.

--mail-type selects email events: END for job end and FAIL for failure. --mail-user sets the recipient. We replace the address or remove both mail lines. Delivery depends on the cluster’s email configuration, and a completion email does not validate the result. The next two pages cover optional GPU and named-node requests.

4.7 · SLIDE 28 · Slurm jobs

When the analysis needs a GPU

A GPU is an additional processor used by software that supports GPU computing. The request needs a GPU partition and account that our group can access. In --gres=gpu:GPU_TYPE:1, gpu identifies the resource, GPU_TYPE is a type name configured on the cluster, and the final 1 asks for one GPU per allocated node. The group’s documentation or support contact can confirm the valid names.

Requesting a GPU does not make CPU-only software use it. Inside an allocated NVIDIA GPU job, nvidia-smi shows the GPU that is visible to the job and basic usage information. GPU memory is separate from the CPU RAM requested with --mem.

The analysis software also needs an environment compatible with that GPU; its installation instructions specify those requirements. The tiny example here stays on CPUs. A related optional request is choosing a particular compute node, which is different from choosing a GPU type.

4.8 · SLIDE 29 · Slurm jobs

When a particular node is required

--nodes and --nodelist answer different questions. --nodes=1 asks for one computer. --nodelist=NODE_NAME asks for a particular named computer. NODE_NAME must be replaced by a real compute-node name in a partition that our account can use; a login-node name does not belong here.

sinfo shows cluster resources. In this command, -p selects the partition, and -N displays information by node. Seeing a node in the output does not grant permission to use it.

Most jobs can let Slurm choose any node that satisfies the resource request. Choosing one particular machine narrows the choice and may increase waiting. It can be useful when a group requires that machine for a hardware-specific test or comparison. If the real need is simply more memory or a GPU type, requesting that resource may be enough. Watch job output and search the error log

The two tail commands answer different questions. tail -n 20 shows the last twenty lines and then returns to the prompt. tail -f keeps watching the file and displays new output as it is written. The filename must contain the current job’s ID.

While tail -f is active, this terminal is occupied by the viewer. Ctrl+C stops that viewer and returns to the prompt; the batch job continues. Cancelling the job requires scancel with its job ID.

After leaving tail, grep searches the error log. In -in, i ignores letter case and n adds line numbers, so we can locate matching messages. A match needs interpretation, and no match does not prove success. Programs may write ordinary status messages to the error stream, so a nonempty .err file is not automatically a failure.

Logs help explain what happened. Next we will also open the actual output file and check what the analysis produced.

Common errors and the first useful check

An error message gives us a starting point. Repeating the same submission without changing anything usually repeats the problem.

For a missing file, check the working folder, the path, and capitalization. For a missing command, check its spelling and whether the required software module or environment is selected. A missing Python or R package must be installed in the environment the job actually uses.

OUT_OF_MEMORY means the job exceeded its memory allowance; TIMEOUT means it reached its time limit. Compare --mem and --time in the job file with the error log and the software’s documented requirements before changing them. An invalid account or partition needs the approved allocation and queue pairing. For a quota error, run quota to see usage and limits. For Permission denied, confirm with the group that you have write access to the target folder.

When asking for help, include the job ID, batch script, exact error, and software version. These details let the lab contact or ICC support reproduce the context without needing passwords or a large dataset.
