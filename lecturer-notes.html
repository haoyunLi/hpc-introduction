1.1 · SLIDE 02 · Access

Prepare files on login nodes; run jobs on compute nodes

Let’s start with what we’re connecting to. HPC means high-performance computing. A cluster is a group of connected computers, and each computer is a node. In this official NCSA overview, our laptop connects to the head node, which we’ll call the login node.

We organize files, edit scripts, and submit work there. Other users share this node, so heavier analysis goes to compute nodes. We submit a job—a request saying what to run and which resources it needs. The scheduler starts it when those resources become available.

Login and compute nodes can reach the same project files through shared storage. We can prepare a script on one node and run it on another. Connecting with VS Code gives us file access; it doesn’t reserve compute resources. Before connecting, we need an approved account and access to our group’s resources.

2.5 · SLIDE 09 · Files in VS Code

Choose home, project, or scratch storage

Home, project, and scratch storage have different purposes. Home, under /u followed by our NetID, is for settings and small personal files. Its quota, or storage allowance, is limited: 100 GiB as the documented soft limit and 103 GiB as the hard limit. Staying above the soft limit for seven days stops new writes until usage falls. The quota can’t be expanded, so large datasets belong elsewhere.

Project storage holds group data, software, and outputs. Capacity depends on the group’s allocation. It has no snapshots—saved filesystem states for restoring earlier files—so important data need separate backups.

Scratch, shown as /scratch/YOUR_NETID, is temporary workspace for files we’re actively working with. Files are typically deleted after 30 days without access, sometimes sooner when space is tight. Purged files can’t be recovered, so move valuable outputs elsewhere.

We’ll use our group’s writable project location. /projects/YOUR_GROUP is a placeholder for its full path, and YOUR_NETID stands for our own NetID. We’ll open the project location, then put demo inside it.

4.1 · SLIDE 24 · Slurm jobs

Slurm runs work on allocated resources

To run a job, we need the cluster to give it some resources. That’s Slurm’s job. It’s the scheduling software in the middle of this diagram.

We prepare a script on the login node and submit it with sbatch. If the requested resources aren’t available, the job waits in a queue. When they become available, Slurm allocates them—reserves them for our job—and the program runs on a compute node.

Both nodes access the same approved project folder, so our inputs, scripts, and outputs stay there. We don’t copy the project to another computer for each run.

Our terminal stays on the login node. The batch job runs separately and can continue after we disconnect. Later, we’ll use srun to request an interactive compute shell for software setup. First, let’s open hello.sbatch.

SchedMD · sbatch
4.3 · SLIDE 26 · Slurm jobs

Set nodes, tasks, CPUs, memory, and time for a job

I find these settings easier to understand by counting the boxes. The big box is one node, so one computer. In this illustration, we request two tasks across the whole job. Each task represents a program process, and each one has two CPUs reserved. Two tasks times two CPUs per task gives us four CPUs in total.

The ntasks value already counts tasks across the whole job. We don’t multiply it by the number of nodes again. And a task here doesn’t mean a sample or an input file.

These boxes show the resources we’re requesting. They don’t show every CPU physically inside the computer. Depending on the system, a Slurm CPU can mean a core or a hardware thread.

Requesting resources also doesn’t automatically make a program use them. For example, python analysis.py starts one process. Running several processes needs suitable software and a launcher, and a program that uses several threads needs its own worker or thread setting.

Our actual hello job is smaller than this illustration: one node, one task, and one CPU. The --mem=1G asks for one GiB of working memory per node, separate from disk storage. The --time value is in hours, minutes, and seconds, so 00:05:00 means five minutes of running time. Queue waiting isn’t included. For a real analysis, we’d choose these values to match the software and data.

For hello, we can keep these small settings. Now we’re ready to submit it.

Checking the queue and stopping a job

squeue -u YOUR_NETID lists our jobs. Replace YOUR_NETID with your username; -u selects the user. Each run gives a fresh snapshot, so run it again to check for changes.

4.6 · SLIDE 29 · Slurm jobs

Output files and email notifications

These lines control where the analysis job’s messages go. They’re already in the supplied analysis.sbatch template, before the commands that load software and run the analysis.

--output names the file for ordinary program output. --error names the file for errors and other diagnostic messages. Some programs also put normal progress messages there, so an .err file doesn’t automatically mean the job failed. We need to read what it says.

The useful part of these names is %j. We leave that in the script, and Slurm replaces it with the job ID. So, for job 123457, analysis-%j.out becomes analysis-123457.out. That gives each submission its own named log.

With these filenames, the logs go into the folder we submit from. If we add a subfolder to the path, we need to create that folder before submitting.

Email is optional. --mail-type chooses the events: END when the job ends, and FAIL for failure. --mail-user gives the recipient. We put our own address there, or remove both mail lines if we don’t want email. Delivery depends on the cluster’s email setup, and we still check the results even if we receive a completion email.

That covers the usual messages and notifications. Next are two optional resource requests, starting with a GPU.

4.7 · SLIDE 30 · Slurm jobs

When the analysis needs a GPU

Some tools use a GPU, an additional processor for software that supports it. We need an account and GPU partition our group can access. The partition line selects that queue, and --gres requests the GPU resource.

In gpu:GPU_TYPE:1, GPU_TYPE is the configured type name, and the final 1 requests one GPU per allocated node. We get valid partition and type names from our group’s documentation or support contact.

Reserving a GPU won’t make a CPU-only program use it. Inside an allocated NVIDIA GPU job, nvidia-smi shows the visible GPU and basic usage information. Its memory is separate from the CPU RAM requested with --mem.

The software also needs a compatible environment, so we follow its installation instructions. Our demo stays on CPUs. Next is choosing a particular compute node: a GPU type describes hardware, while a node name identifies a computer.

4.8 · SLIDE 31 · Slurm jobs

When a particular node is required

A GPU type specifies hardware. A node name asks for a particular machine.

--nodes=1 means “give me one computer.” --nodelist=NODE_NAME means “give me this particular computer.” That must be a compute node our account and partition allow, not a login node.

sinfo lets us inspect resources. -p selects a partition, and -N shows the information by node. Seeing a machine listed doesn't guarantee that our account can use it.

I'd normally let Slurm choose. Naming one machine gives the scheduler fewer choices and may increase the wait. It can help with a hardware test or comparison, but if we need more memory or a certain GPU, we can usually request that resource directly.

Common errors and the first useful check

I'd read the error before submitting the same file again.

No such file or directory means checking pwd, the path, spelling, and capital letters. For Command not found, check spelling and the selected module or environment. A missing Python or R package means checking the environment the job actually uses and installing it there.

OUT_OF_MEMORY means the memory allowance was exceeded. TIMEOUT means the time limit was reached. We'd consult the log and software requirements before changing --mem or --time.

For an invalid account or partition, check that --account and --partition are an approved pair. quota shows storage usage and limits. Permission denied means checking whether our group gave us write access to that folder.

These are starting points. If the first check doesn't explain the problem, we can take the exact message to our group or ICC support rather than repeatedly submitting the unchanged job.
