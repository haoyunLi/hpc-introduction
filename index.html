Let’s start with what we’re actually connecting to. HPC stands for high-performance computing. A cluster is a group of connected computers, and one computer in that group is called a node. This is the official NCSA overview. Our laptop connects to the head node in the picture—the login node we’ll use in this talk.

Think of that login node as our starting point. We can organize files, edit scripts, and submit work there. It’s shared with other users, so we send the heavier analysis to compute nodes. We do that by submitting a job: a request that says what to run and how much computing power it needs. The scheduler waits until the requested resources are available, then starts the work.

The login and compute nodes can reach the same project files through shared storage. That’s why we can prepare a script in one place and run it on another node. Connecting with VS Code gives us access to those files; getting compute resources is a separate step. First, though, we need an approved account and permission to use our group’s resources.

ICC · Storage and Data
09 / 45

Before putting files on the cluster, we need to choose a place for them. Home, project, and scratch storage serve different purposes.

Home is under /u, followed by our NetID. It’s for settings and small personal files. Its quota—the amount of space we’re allowed to use—is very limited: 100 GiB as the documented soft limit and 103 GiB as the hard limit. Staying above the soft limit for seven days stops new writes until we bring our usage down. This quota can’t be expanded, so home is a poor place to keep large datasets.

Project storage is shared by the group. Its capacity depends on the group’s allocation, and it’s where we can keep group data, software, and outputs. It has no snapshots, meaning saved filesystem states that could restore earlier files. Important data therefore need a separate backup plan.

Scratch is temporary working space. Files are typically deleted after 30 days without access, and sometimes sooner when space is tight. Purged files can’t be recovered, so any outputs we want to keep need to be moved elsewhere.

For this walkthrough, we’ll use the writable project location our group gives us. /projects/YOUR_GROUP is only a placeholder for that full path, just as YOUR_NETID stands for our own NetID. We’ll open the project location first, then put our demo folder inside it.

Suppose we want a quick look at the start of our input table. We can use head -n 5 data/samples.csv. It’s easier to read if we take it in three parts.

head is the program. The option -n, followed by the value 5, asks for the first five lines. Then data/samples.csv is the file to read. If the file has fewer than five lines, head just shows the lines that are there.

Everything after head is an argument. Some arguments change what a command does; others give it a value or a file path. Option letters belong to individual commands, so -n can mean something different in another program.

Spaces usually separate arguments. Quotes keep a path together when it contains spaces. The quoted version shown here also works, although data/samples.csv doesn’t need quotes because it has no spaces.

There’s one more piece we need for this example: data/samples.csv is a path relative to our current folder. So before reading or running anything, we need to know where the terminal is working.

Once we can see our files, we’ll often want to organize them. VS Code’s Explorer can do most of this too, but these commands come up a lot in instructions. They’re examples we can choose from, so we don’t need to run every line to set up the demo.

When a job fails, I'd start with the message before submitting the same file again. It often points to a specific part of the setup.

For No such file or directory, pwd tells us where we're working. Then we'd check the path, spelling, and capital letters. For Command not found, we'd check spelling and whether the right module or environment is selected. A missing Python or R package means checking which environment the job actually uses and installing the package there.

OUT_OF_MEMORY means the job exceeded its memory allowance. TIMEOUT means it reached its time limit. We'd look at the log and the software's requirements, then review --mem or --time accordingly.

An invalid account or partition means checking that --account and --partition are an approved pair. For a quota error, quota shows usage and limits. Permission denied is a reason to check that our group has given us write access to the folder.

If we need help, the job ID, batch script, exact error, and software version give someone a concrete starting point. We don't need to send a password or the whole dataset. The official guide and ICC support are good places to turn when we need more help.
